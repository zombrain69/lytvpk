# LytVPK 分类命名规范化（`分类-替换对象-原标题`）可行性评估

> 路线图第 8 项③。评估对象：把库内 Mod 文件名规范化为参考体系 `分类-替换对象-原标题.vpk`
> （参考实现 `sHartet/l4d2-addons` 的 naming-rules v1.2，含 63 字节主干上限）。
> 本文件只做核查与设计草案，不代表已实施；需要用户拍板的点见 §6。

## 1. 参考体系要点（可移植的部分）

- 目标形式 = `分类-替换对象-原标题.vpk`：**原标题永不改动**（仅做 Windows 非法字符全角化
  `\ / : * ? " < > |` → `＼ ／ ： ＊ ？ ＂ ＜ ＞ ｜`）；分类前缀与替换对象由规则推得。
- **63 字节硬上限**：主干（不含 `.vpk`）超 63 个 **ANSI** 字节的包引擎静默不挂载
  （列表看不到、内容全不加载、无任何报错）；实测 82B / 88B 完全无效、同一份字节改成 41B
  立即生效、58B / 61B 一直正常。超长标题必须**只截断标题段**（先按空格断词，再按字符断，
  去掉尾部 ` - .`），前缀与替换对象永不缩短。按 63 字节算中文约可用 30 字。
- 分类词表：物件域 10（`生还者- 特感- 普感- 主武器- 副武器- 近战- 投掷物- 消耗品- 场景道具- 场景-`）
  ＋ 资源类型 7（`模型- 地图- 音效- 界面- 特效- 脚本- 材质-`）＋ 兜底 `其它-`；
  专项 2（`手电筒-`、`管理员插件-`，放在物件域判定之后、优先于资源类型，附 ≥25% 占比门槛
  防「附带覆盖」误判）。
- 判定顺序 S1–S5（命中即止）：地图（`maps/*.bsp|nav`）→ 物件域【高置信：物件标签 ＋
  含模型文件 ＋ 域相关路径占比 ≥5%】→ 物件域·贴图版【中置信，列入待复核】→ 资源类型
  （取路径数最多的资源标签）→ 保留原前缀【低置信：'未归类' 占比 >50% 等】；
  横切行（骨架动画/手势/语音/残肢…）不参与中段取值、同域多行取「上位名」。
- 纪律：**幂等**（规范库上重跑必须 0 改动；剥旧前缀用**前缀匹配式**而非按短横切分——
  替换对象自带短横，如 `AK-47 突击步枪`）；规则例外表（用户裁定落 `name_exempt.json`）；
  执行管线 = 重扫 → 自解析路径 → 推演（plan）→ 出批次 JSON → **干跑** → 执行
  （`.vpk` ＋ 同名图片 ＋ `.url` 三件同步改名）。实测基准：127 个 mod 中 74 个需改名，
  低置信 6 条列「待复核」不静默猜。

## 2. LytVPK 现状盘点（可复用基建）

### 2.1 标签体系 = 现成的「分类前缀」落盘通道

- 非工坊文件：标签以 `[主标签+副标签]名字.vpk` 落盘（`SetVPKTags` → `setVPKTagsLocked`：
  改文件名 ＋ addonlist 键迁移）；工坊文件走同名 `.meta`（**不改文件名**，避免 Steam
  与游戏失去识别）。
- 双端解析同形：Go `parser.ParseFilenameTags`（`^(_)?\[(.*?)\](.*)$`，`+`/`,` 拆分，
  第一段为主标签）；前端 `rename-edit.mjs` 的 `parseFilenameTags` 同形。
- 与参考的差异：现体系是**内容标签**（主 4 类 `地图/人物/武器/其他` ＋ 细副标签，
  如 `ellis`/`ak47`），与参考的 20 前缀**不是同一张表**（参考把角色细分到
  `生还者-/特感-`，LytVPK 先归 `人物`）。

### 2.2 识别引擎：「替换对象」信号已存在

- `VPKFile` 已有：`ContentSubjects`（资源路径证据识别出的实际主体）、`VoiceCharacters`
  （标准 `sound/player` 语音目录 → 替换角色）、`SubjectSummary`（如「主体：Coach 语音」，
  置信度 高/中/低）、`XDRSlots`（xdReanimsBase 角色/模型/slot 证据）。
- 主体命名即**英文名**（Coach/Boomer…），与参考「生还者/特感用官方英文名」的口径一致。
- 尚未覆盖：部位「上位名」（副武器→`手枪`、主武器→`霰弹枪`）、横切行与多域优先级、
  「域相关占比 ≥5%」一类阈值——需在命名规则层补齐。

### 2.3 63 字节：只有体检、没有截断器

- 体检已有 `filename_too_long`（警告；只报告不改名）——与参考同一硬约束，只读抽样里
  仅 1 个超长文件。
- 缺 `cap_name()` 等价物：把主干截断到 ≤63 ANSI 字节（**只动标题段**）。移植成本低，
  适合先写成 Go 纯函数 ＋ 单测（含幂等：截断后重跑不再变）。

### 2.4 重命名机制：单文件全链路已就绪

- `RenameVPKFile`：只读闸门 → 文件名合法性校验 → `[标签]` 保留（无标签新名自动补回旧标签）
  → 同名侧车（`.meta`/图片/`.url`）跟随 → 缓存更新 → **addonlist 键迁移**
  （`rebindModKeyOnRename`，覆盖策略组/分层/依赖/忽略清单）→ 冲突复检失效 →
  下载任务路径更新。
- 前端：重命名弹窗（预填、长度提示 255/260、按 addoninfo 标题填充）、操作前
  `confirmVPKOperationWarning`。
- **没有批量重命名**（全代码库无相关入口）——批量命名器要从零搭 UI 与计划器。

### 2.5 本轮前置修复（b4f932f）

- 核查中发现：重命名弹窗预填曾把标签文字拼进输入框（`[Airi]A.vpk` 编辑保存后变成
  `[Airi]AiriA.vpk`；`_[标签]` 组合还会丢首字符）——上游 06712f8 重构引入的回归。
- 已修复并抽出 `rename-edit.mjs`（22 项测试，含往返幂等与接线断言）。
  批量命名器必须与它共用同一「标签保留」口径，否则同类翻倍/丢字会在批量场景被放大。

## 3. 差异与缺口（要做到参考体系还缺什么）

| 环节 | 参考体系 | LytVPK 现状 | 缺口 |
| --- | --- | --- | --- |
| 分类词表 | 20 前缀（物件域细分＋资源类型＋专项） | 4 主标签＋细副标签 | 映射层/词表决策（§6-①） |
| 替换对象 | 英文名（生还者/特感）/中文名（其余）＋上位名 | ContentSubjects/VoiceCharacters（英文名） | 上位名表、横切行、多域优先级 |
| 判定置信 | S1–S5＋占比阈值＋待复核 | 标签识别 v2＋Evidence/置信度 | 两套体系的对齐编排 |
| 63B 截断 | cap_name（干跑可见） | 体检只报告 | Go 版截断器（含幂等） |
| 批量执行 | 批次 JSON＋干跑＋三件套同步 | 单文件全链路 | 计划器/预览/执行/汇总 UI |
| 幂等 | 重跑 0 改动 | 单文件天然幂等（预填＝原名时无操作） | 前缀匹配式判定进计划器 |

## 4. 设计草案（分阶段）

- **P0（已完成，b4f932f）**：重命名预填回归修复（§2.5）。
- **P1 · 单文件「规范化预填」**：重命名弹窗加「按分类建议填充」入口——后端（parser 派生）
  给出 `分类-替换对象-原标题` 建议（含 cap_name 截断与非法字符处理），用户可改再保存；
  复用现有单文件链路（标签保留、addonlist 迁移）。价值：立即可用、零批量风险，
  先把「建议质量」摆给用户验收。
- **P2 · 批量改名计划器**：菜单入口 → 扫描生成计划（幂等；低置信与跳过明细）→ 应用内预览
  （旧名 → 新名对照 ＋ 63B/路径长度提示 ＋「待复核」分组）→ 确认 → 逐项执行
  （复用 `RenameVPKFile`）→ 结果汇总＋失败逐项报告；计划可导出（含撤销清单）。
  写盘纪律对齐 addonlist 写前差异确认（预览与写入同口径）。
- **P3 · 规则对齐与例外**：S1–S5 移植、横切行/上位名、占比阈值、例外表（用户裁定持久化）。

## 5. 风险与护栏

- **改名影响面**（基建均已就位）：addonlist 键、策略组/分层/依赖记录、`.meta`/`.url`
  侧车、下载任务路径；**工坊文件不改名**（沿用 `.meta` 通道）——批量器必须显式跳过
  `workshop\` 位置文件（参考体系也只作用于「整理后的库」）。
- **不可逆感**：本地改名有完整回滚数据（计划清单旧↔新），但仍必须应用内确认＋逐项失败报告。
- **63B 截断只动标题段**；前缀与替换对象永不缩短（参考硬规则，直接沿用）。
- **算错就翻倍/丢字**：b4f932f 的教训——所有改名合成逻辑必须单调、幂等、有往返测试。
- 规则低置信时**保留原名＋待复核**，不静默猜（参考 S5 纪律，与 LytVPK「过度打标可接受、
  漏标不可」相反：命名要用更保守的口径）。

## 6. 结论与决策点

**可行性：高。** 单文件链路、标签保留、addonlist 迁移、侧车、只读闸门、体检（63B）都在；
需要新增的只有「命名规则层」（词表映射＋替换对象提取＋CapName＋幂等）与批量 UI。

给用户（在场时）的决策点：

1. **词表策略**：命名「分类」直接采用参考 20 前缀（贴近已定稿规则，但与本应用现有
   4 主标签体系双轨并存），还是把现有标签体系扩到等价粒度（一套体系，工程量更大）？
2. **范围与节奏**：先做单文件「建议预填」（P1，立即可用），还是一步到批量规范化全库（P2+）？
3. **规则来源**：把参考规则全文移植为内置默认，还是做成可配置（含例外表 UI、待复核清单）？

> 记录（2026-10-12）：**词表策略已定 —— 默认采用参考 20 前缀**（与本应用 4 主标签体系
> 双轨并存），随时可换；P1 已按此实施（行名暂用本应用标签词汇，见「实施进展」）。
