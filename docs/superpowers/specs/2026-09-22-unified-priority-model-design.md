# 统一优先级模型设计（对齐 FireAxe 的深层理解）

> 参考：FireAxe `AddonNode.Priority` / `PriorityInHierarchy`、`AddonGroup`（组优先级累加）、
> `AddonConflictUtils`（只在同优先级内判冲突）、`AddonRoot.Push`（按优先级降序写 addonlist）。
> 基线 commit：`f8aa1cf1391802c64525412fdf326dbe0ecc98b1`（v0.7.3）。
>
> LytVPK 已有基础：`internal/app/conflict.go` 的优先级感知判定已使用 addonlist 顺序号；
> `AddonListLoadOrderEntry` 已向前端暴露顺序与开关。

## 1. FireAxe 的优先级模型为什么更完整

1. **优先级是显式数值**，用户可编辑、可排序、可解释，而不是"文件里的第几行"。
2. **全局优先级 = 自身优先级 + 所属组优先级**：给组调一次数值，就能整体抬升或压低一批 Mod。
3. **同优先级内不保证先后**，因此同层重叠被视为真冲突；跨层重叠是用户有意的覆盖。
4. 冲突判定、列表排序、push 写盘顺序**共用同一个数值**，不会出现"检测说没事、游戏结果却是另一个"。

相比之下 LytVPK 的现状有三个缺口：加载顺序是隐式序号（用户看不到、改不动"数值"）；
策略组只带启用策略、没有权重；冲突检测只能用"顺序号是否相同"近似"同层"，
而顺序号天然两两不同，分层语义名存实亡。

## 2. 目标与非目标

目标：

1. 引入**用户可编辑的优先级分层**（整数，语义与 FireAxe 一致：越小越先加载）。
2. 支持**组权重**：策略组的权重叠加到成员，得到"有效分层"。
3. 冲突判定、排序展示、写入顺序**共用同一套有效分层**。
4. **未设置分层时，行为与现状逐字节一致**——这是硬约束，必须有回归测试守住。

非目标：

- 不把分层做成独立于 `addonlist.txt` 的平行真相：**顺序仍是游戏侧唯一权威**，
  分层只承担"意图表达 + 判定 + 排序"。
- 不改 push 语义（LytVPK 直接写 addonlist，没有符号链接 push）。
- 不引入 FireAxe 的 `RefAddonNode`（同一 Mod 多方案已由"启用方案"覆盖）。

## 3. 数据模型

```go
// 每个 Mod 可选的分层；缺省（无记录）表示"未分层"。
type ModPriorityEntry struct {
    Key       string `json:"key"`
    Name      string `json:"name"`
    Tier      int    `json:"tier"`      // 越小越先加载，可为负
    UpdatedAt string `json:"updatedAt"`
}

// 存放于配置目录 priority.json（与 profiles.json / groups.json / dependencies.json 同级）。

type ModStrategyGroup struct {
    // ……既有字段保持不变……
    Tier int `json:"tier"` // 组权重：叠加到组内成员的有效分层
}
```

**有效分层**（唯一判定入口，所有模块只能通过它取优先级）：

```text
base(mod)      = ownTier(mod) 若已设置，否则 = 该 Mod 在 addonlist.txt 中的顺序号
effective(mod) = min(base(mod), min{ g.Tier | g 是包含 mod 且设置了 Tier 的策略组 })
```

**为什么组权重取 `min` 而不是像 FireAxe 那样相加**：
FireAxe 的 addon 树是层级结构，每个节点只有一条父链，累加语义明确；
LytVPK 的策略组是**可重叠的集合**且可随时增删成员，累加会让"同一 Mod 同时属于两个组"
产生不可解释的漂移。取 `min` 保证：组权重只能**抬高优先级**（更靠前加载），
不会因为分组数量变化而反复漂移，并且同一 Mod 属于多个组时结果唯一可预测。

## 4. 判定与排序

1. **冲突判定**：对每个重叠的参与者集合计算 `effective`；
   - 存在两个及以上相同的 `effective` → **真冲突**（意图上不可分辨谁该覆盖谁）；
   - 全部互不相同 → **覆盖关系**，胜者 = `effective` 更大者（最后加载并覆盖），
     并列展示时用顺序号作为次级说明。
2. **排序/写盘**：按 `effective` 升序、同层内保持现有相对顺序（稳定排序）写回 `addonlist.txt`；
   写盘必须走既有 `writeAddonList`（保留编码/BOM + 原子替换）并触发备份与受保护快照同步。
   **只有用户显式执行"应用分层"时才重排**，任何隐式路径（开关、体检、方案应用）都不得改变顺序语义。
3. **展示**：列表与冲突卡片显示 `优先级 #顺序号（分层 T）`；排序新增"按分层"选项。

## 5. 兼容与迁移

- `priority.json` 不存在或某 Mod 无记录 → 该 Mod `base = 顺序号`（与现状一致）；
  所有组 `Tier` 缺省为 0？——**不行**：0 会参与 `min`，破坏"未分层不变"。
  因此组权重需要一个显式"未设置"表示：`Tier *int`（nil = 不参与）。
- 升级路径：老用户升级后 `priority.json` 不存在、所有组 `Tier` 为 nil，
  判定与排序结果必须与本设计落地前的黄金结果逐条一致（见第 6 节第 1 条）。
- 方案快照：沿用 `ModEnableProfile.includesAutomation` 机制，新增 `priorities` 字段，
  随自动化快照一起保存/恢复；导入他人方案时按现有校验规则过滤非法条目。

## 6. 测试策略

1. **黄金回归**：未分层时，冲突/覆盖判定结果与实现前逐条一致（用固定 fixture 生成快照对比）。
2. 同层重叠 → 冲突；跨层重叠 → 覆盖，且胜者为 `effective` 更大者。
3. 组权重 `min` 生效；同一 Mod 属于两个不同权重组时取更小值；组 `Tier` 为 nil 时不参与。
4. 排序写入：`effective` 升序、同层稳定；写盘后能被现有解析器读回；编码/BOM 保持不变。
5. 方案快照携带分层并在应用后恢复。
6. 边界：负数层级、极大值、同一 Mod 重复设置（后者覆盖前者）、删除分层后回到顺序号。

## 7. 开放问题（实现时确认）

- 分层数值的 UI 形式：默认直接填数字，另提供 ±1 快捷按钮。
- 是否需要"锁定"标志：锁定后不随方案应用被覆盖。
- 与随机轮换的交互：轮换只改开关，不改分层（实现时用测试固定该约定）。
